# Polaris YTM / Bluetooth AVRCP Browsing — proof of concept

**Separate experiment.** Original Polaris main Android app is unchanged.
This is **not** a new APK. Do not merge any of this into the current
in-car media service until the real Bluetooth folder transfer is observed.

## Why this route?

Android Automotive's Bluetooth head unit is an **AVRCP Controller (CT)**.
The Android phone is an AVRCP **Target (TG)**. On the phone the Android system
Bluetooth service (not an ordinary app) can browse a music app's
MediaBrowserService and relay its folder/items back to the paired controller.

This explains why a Polestar 4 can display YouTube Music's Home/Library
via Bluetooth while a normal third-party Polaris app receives
MediaBrowser.onConnectionFailed() from the same YouTube Music service.

The system Bluetooth role is privileged. Simply requesting BLUETOOTH_CONNECT
on the *same phone* does not grant access to the remote AVRCP Controller
profile, and does **not** turn an ordinary app into com.android.bluetooth.

Sources:
- https://source.android.com/docs/automotive/ivi_connectivity
- https://developer.android.com/media/legacy/audio/mediabrowserservice
- https://github.com/BimmerGestalt/AAIdrive/discussions/525
- https://manpages.debian.org/testing/bluez/bluetoothctl-player.1.en.html

## Minimal real test using a Linux Bluetooth audio receiver

Requirements: Linux with **Bluetooth Classic BR/EDR**, BlueZ (bluetoothctl),
and A2DP Sink + AVRCP Controller stack active. Some PCs need PipeWire/WirePlumber
or PulseAudio configured as an A2DP **sink**, rather than the default source.
Do not assume a Bluetooth adapter alone is sufficient.

1. On the Linux receiver, verify with "bluetoothctl list" that an adapter exists.
2. Pair the phone playing YouTube Music to the Linux receiver as Bluetooth media
   audio, and ensure both profiles connect. This may redirect the phone's
   audio away from the car, so **test parked / outside a driving session**.
3. Open bluetoothctl and type these commands, one per line:

       menu player
       list
       show
       list-items 0 19

   - If "list" has **no remote player**, the Bluetooth role/profile isn't
     active: stop. This is not a YouTube Music failure.
   - If the player exists but isn't Browsable, test while a real YTM track is
     playing; the app might expose the browse tree only when active.
   - If "list-items" lists Home, Library or another folder, this is a genuine
     **Bluetooth AVRCP browse success**.
   - Use "change-folder <path returned by list-items>" then "list-items"
     to test one real folder. Paths are generated by BlueZ, not invented.

4. Optional structured diagnostic:

       sudo apt-get install bluez python3-dbus
       /usr/bin/python3 tools/ytm_avrcp_probe.py --json

   Reads org.bluez.MediaPlayer1 and org.bluez.MediaFolder1.ListItems from
   the Linux machine. No Google credentials. It does NOT call Play(), change
   folders or send control commands, nor does it copy artwork. Bounded to
   the first 20 root items. If unavailable, exits nonzero.

## Results and next design gate

Proceed to a proxy only if the genuine AVRCP browser returns actual YTM folders
and media items from the test handset.

Tentative optional architecture (not yet built):

    YT Music on phone
      -> Bluetooth system service
      -> paired Linux AVRCP controller
      -> local trusted Wi-Fi API
      -> Polaris Android Auto media browser
      -> user selects item
      -> AVRCP controller PlayItem
      -> YT Music starts on phone

Final selection/PlayItem is a **separate unverified step**; initial list success
does not prove item playback or stable music routing. It also introduces an
additional always-on device that may conflict with the car's Bluetooth audio.
Prefer the car's own YTM UI if extra hardware is unacceptable.

### Hardware note

An ESP32-S3 supports BLE only, not Classic Bluetooth AVRCP. Do not attempt
this proof-of-concept with the ESP32-S3 CAN controller. Original ESP32 chips
support Classic BT, but ESP-IDF controller API support for **folder browsing**
must be verified independently before committing to firmware.
